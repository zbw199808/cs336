## 1. 评估的框架与思考方式

### 1.1 评估不是机械过程

评估**决定了语言模型的未来方向**——你优化什么指标，模型就往什么方向发展。

### 1.2 评估的四个目的

| 目的 | 角色 |
|------|------|
| 购买决策 | 用户/公司选择模型 A 还是模型 B |
| 能力测量 | 研究者衡量模型的原始能力 |
| 影响评估 | 理解模型的收益与危害 |
| 改进反馈 | 开发者获取改进方向 |

### 1.3 评估框架四问

1. **输入**：覆盖了哪些用例？是否包含困难的长尾输入？
2. **调用方式**：如何 prompt？是否使用 CoT、工具、RAG？评估模型还是系统？
3. **输出评估**：参考答案是否无误？用什么指标？如何考虑成本和不对称误差？
4. **结果解读**：91% 意味着什么？如何处理训练-测试重叠？评估的是模型还是方法？

## 2. Perplexity 评估

### 2.1 定义

$$\text{Perplexity} = (1/p(D))^{1/|D|}$$

衡量模型 p 是否给数据集 D 分配了高概率。

### 2.2 历史演变

- **早期**：在固定数据集（Penn Treebank, WikiText-103）上训练和测试
- **GPT-2**：在 WebText 上训练，零样本测试标准数据集（跨分布评估）
- **GPT-3 后**：转向下游任务准确率

### 2.3 Perplexity 仍然有用的原因

- 比下游任务准确率**更平滑**（适合拟合 scaling laws）
- **通用性**（训练就用它，不会遗漏某些细微差别）
- 可以计算下游任务上的条件 perplexity

### 2.4 Perplexity 极端主义观点

```
真实分布 t, 模型 p
最优 perplexity = H(t), 当且仅当 p = t
如果 p = t → 解决所有任务 → AGI
```

但注意：这可能不是最高效的路径。

### 2.5 类似 Perplexity 的基准

- **LAMBADA**：完形填空任务
- **HellaSwag**：选择最合理的后续

## 3. 知识基准 (Knowledge Benchmarks)

### 3.1 MMLU (Massive Multitask Language Understanding)

- 57 个学科，多选题
- 本质上测试**知识**而非语言理解
- 用 few-shot prompting 评估

### 3.2 MMLU-Pro

- 去除了 MMLU 中的噪声/简单题
- 4 个选项扩展到 10 个
- 使用 CoT 评估
- 模型准确率下降 16%-33%（未饱和）

### 3.3 GPQA (研究生级 Q&A)

- 61 位 PhD 承包商在 Upwork 上出题
- PhD 专家达 65% 准确率
- 非专家（30 分钟+Google）达 34%
- GPT-4 达 39%

### 3.4 Humanity's Last Exam

- 2500 题，多模态，多学科
- $500K 奖金 + 联合作者资格
- 经前沿 LLM 过滤和多轮审查

## 4. 指令遵循基准

### 4.1 Chatbot Arena

| 特点 | 描述 |
|------|------|
| 输入 | 互联网用户的实时输入 |
| 方法 | 双盲对比两个模型的回复 |
| 评分 | 基于两两比较的 ELO 分数 |
| 优势 | 实时、动态、可加入新模型 |

### 4.2 IFEval

- 给指令添加简单合成约束（如"用不超过 100 词"）
- 约束可自动验证，但语义不验证

### 4.3 AlpacaEval

- 805 条指令
- 与 GPT-4 preview 对比的胜率（GPT-4 也当裁判，可能有偏见）

### 4.4 WildBench

- 从 100 万人机对话中精选 1024 例
- GPT-4 turbo 做裁判 + checklist
- 与 Chatbot Arena **相关性 0.95**（成为基准的"合理性检查"）

## 5. 智能体基准 (Agent Benchmarks)

**Agent = 语言模型 + 脚手架逻辑**

### 5.1 SWE-Bench

- 12 个 Python 仓库的 2294 个任务
- 给定代码库 + issue 描述 → 提交 PR
- 用**单元测试**评估

### 5.2 CyBench

- 40 个 CTF (Capture the Flag) 任务
- 用首次解决时间衡量难度

### 5.3 MLEBench

- 75 个 Kaggle 竞赛
- 需要训练模型、处理数据等

## 7. 安全性基准

### 7.1 HarmBench

- 510 种违法或违规行为
- 测试模型是否会产生有害输出

### 7.2 AIR-Bench

- 基于监管框架和公司政策
- 314 个风险类别，5694 条 prompts

### 7.3 Jailbreaking

**GCG (Greedy Coordinate Gradient)**：
- 自动优化 prompts 以绕过安全机制
- 从开源模型 (Llama) **迁移**到闭源模型 (GPT-4)

### 7.4 安全性的复杂性

- **Capability vs Propensity**：能做 vs 愿意做
- API 模型：propensity 重要
- 开源模型：capability 重要（安全微调可被移除）
- **双重用途**：网络安全 Agent 可攻可防

## 8. 现实性与有效性

### 8.1 两种 Prompt 类型

| 类型 | 描述 | 价值 |
|------|------|------|
| 测验型 (Quizzing) | 用户知道答案，测试系统 | 评估能力 |
| 求助型 (Asking) | 用户不知道答案，寻求帮助 | 产生实际价值 |

### 8.2 训练-测试重叠

- 基础模型时代有清晰的 train/test 分割
- 现在：在互联网上训练，数据不公开
- 检测方法：利用数据点的可交换性推断重叠

### 8.3 方法 vs 模型/系统评估

| 评估对象 | 规则 | 鼓励 |
|---------|------|------|
| **方法** | 标准化 train/test split | 算法创新 |
| **模型/系统** | 什么都行 | 工程集成 |

**例外**：nanogpt speedrun（固定数据和计算时间）、DataComp-LM（固定训练流程）

## 总结

| 要点 | 内容 |
|------|------|
| 没有唯一正确的评估 | 根据目标选择评估方式 |
| 始终检查个体实例 | 平均数字可能掩盖问题 |
| 多维度考虑 | 能力、安全、成本、现实性 |
| 明确游戏规则 | 评估方法还是系统 |
